本篇是 Week 4 的 B+ 树总结，把索引从"结构长什么样"到"怎么并发改"这条线串起来：先是结点布局与核心性质，再到查找/插入/删除的基本操作，然后是墓碑延迟删除和迭代器这两个工程化细节，最后是并发控制和与其他索引结构的对比。

## 1. B+树的基础

### 1.1 定义

B+ 树是一种自平衡、有序的 m 叉树，支持查找、顺序访问、插入和删除，复杂度均为 O(log n)。内部节点仅保存用于索引导航的分隔键和子节点指针，所有实际的键值对存储在叶子节点中；所有叶子节点位于同一层，并通过链表连接，从而同时支持高效的点查询和范围查询。节点在插入和删除过程中通过分裂、借用和合并操作维持树的平衡。

结构示例：

```text
              [20]                    ← 根节点（内部节点）
             /    \
          <20      ≥20
         [10]      [35]               ← 内部节点
        /    \    /    \
      <10  ≥10  <35  ≥35
    [6|10] [20|31] [38|44]            ← 叶子节点（键从低到高）
      ↓      ↓       ↓                ← 兄弟指针（Sibling Pointers）
```

### 1.2 核心性质

| 性质               | 说明                                                    |
| ------------------ | ------------------------------------------------------- |
| **完美平衡** | 所有叶子节点位于同一深度                                |
| **半满约束** | 根以外的每个节点至少半满：`m/2 - 1 ≤ #keys ≤ m - 1` |
| **子节点数** | 有 k 个键的内部节点有 k+1 个非空子节点                  |
| **块优化**   | 针对读写大数据块优化                                    |

### 1.3 结点结构

每个 B+Tree 节点由键/值对数组组成：

- **键**：从索引目标属性派生。
- **值**：根据节点类型（内部 vs 叶子）不同。
- **数组通常按键排序存储。**
- **NULL 键存储在最前或最后的叶子节点中。**

**叶子节点结构：**

```text
┌──────────────────────────────────────────────────────┐
│ Prev PageID │ Slots# │ Next PageID │ High Key          │
├──────────────────────────────────────────────────────┤
│ Key₁ │ Val₁ │ Key₂ │ Val₂ │ Key₃ │ Val₃ │ …          │
│ Key₄ │ Val₄ │ Key₅ │ Val₅ │                         │
└──────────────────────────────────────────────────────┘
  ← 键/值对按键排序，叶子节点间通过 Prev/Next 链接 →
```

- **Prev/Next PageID**：兄弟指针，链接相邻叶子节点。
- **Slots #**：已用槽数量。
- **High Key**：该节点的键上界（用于并发控制）。

**内部节点结构：**

```text
┌──────────────────────────────────────────────────────┐
│ Slots# │ High Key                                    │
├──────────────────────────────────────────────────────┤
│ Child₀ │ Key₁ │ Child₁ │ Key₂ │ Child₂ │ … │ Childₙ  │
└──────────────────────────────────────────────────────┘
  ← n 个分隔键 + (n+1) 个子指针，按键排序，仅用于导航 →
```

- **Key（分隔键 / Routing Key）**：内部节点只存键、不存值；键只是从子节点"借来"的导航路标。
- **Child（子指针）**：指向下一层节点（叶子或内部节点）的 Page ID。有 n 个键就有 n+1 个子指针。
- **路由规则**：`Childᵢ` 覆盖键区间 `[Keyᵢ, Keyᵢ₊₁)`（令 `Key₀ = -∞`、`Keyₙ₊₁ = +∞`）。查找键 k 时，沿满足 `Keyᵢ ≤ k < Keyᵢ₊₁` 的那个子指针下降。
- **High Key（可选）**：该节点键的上界，供并发控制使用（与叶子节点一致）。

## 2. B+树的基本操作（查找/插入/删除）

### 2.1 查找

1. 从根节点开始，令 `cur = root`。
2. 如果 `cur` 不是叶子节点：
   - 在 `cur` 的分隔键中，找到满足 `Keyᵢ ≤ key < Keyᵢ₊₁` 的区间。
   - 令 `cur = cur.Childᵢ`（沿子指针下降一层），重复第 2 步。
3. 否则 `cur` 即为叶子节点 L，在 L 内定位 key（线性扫描 / 二分）。
4. 如果命中 → 返回该项的值（Record ID / 元组 / 主键）。
5. 否则 → 键不存在。

### 2.2 插入

1. 找到正确的叶子节点 L。
2. 将数据条目按排序顺序插入 L。
3. 如果 L 有足够空间 → 完成。
4. 否则，分裂 L 为 L 和 L₂：
   - 均匀分配条目，复制中间键到父节点。
   - 在 L 的父节点中插入指向 L₂ 的索引条目。
5. 如果父节点也满了 → 递归分裂，推送中间键到上层。

> 关键区别：叶子分裂时**复制**中间键到父节点；内部节点分裂时**推送**中间键到父节点。

### 2.3 删除

1. 从根开始，找到条目所属的叶子节点 L。
2. 删除该条目。
3. 如果 L 至少半满 → 完成。
4. 如果 L 不足半满（`m/2 - 1` 个条目）：
   - **重分配（Redistribute）**：从兄弟节点借一个条目（与 L 有共同父节点的相邻节点）。
   - 如果重分配失败（兄弟也不够富余）→ 合并 L 和兄弟。
5. 如果发生合并，必须从 L 的父节点中删除指向被合并节点的条目。

## 3. B+树的延迟删除（墓碑机制）

### 3.1 定义

延迟删除，也叫 Tombstone（墓碑）机制，是一种"先逻辑删除、后物理删除"的策略。

当叶子结点中的某个 Key-RID 被删除时，并不会马上把它从数组中移除，而是先记录这个元素已经失效。之后查询和遍历时，会把被墓碑标记的数据当作不存在。只有当墓碑积累到一定数量时，才真正执行物理删除和数组移动。

### 3.2 有什么作用

墓碑机制主要有三个作用。

第一，**减少数组移动开销**。叶子结点内部的数据通常是连续存储的，如果每删除一个元素都立即物理删除，那么后面的 Key-RID 都需要向前移动。使用墓碑后，删除时只需要增加一个逻辑删除标记，不必立即移动大量数据。

第二，**减少 B+ 树结构调整的频率**。物理删除会使结点的 size 减小，如果低于最小容量，就可能触发 Borrow、Merge，甚至一路向上传播到父结点。逻辑删除阶段并不会立即减少物理 size，因此可以延迟这些结构调整。

第三，**将多次删除集中处理**。多个删除操作可以先积累为 tombstone，当 tombstone 数量达到上限后，再集中清理较早的删除记录，从而降低频繁物理删除带来的开销。

### 3.3 如何实现

在 Leaf Page 中维护 tombstone 数组和当前 tombstone 数量。删除某个 key 时，先将其对应的物理下标记录为 tombstone，完成逻辑删除；当 tombstone 数量达到上限后，再清理较早的 tombstone，并真正删除对应的 Key-RID。

由于插入、删除和结点分裂都会改变元素位置，因此 tombstone 下标也需要同步调整。查询和 Iterator 遇到 tombstone 时，则直接跳过对应数据。

## 4. 迭代器

### 4.1 定义

迭代器（Iterator）是用于按照 key 的有序顺序访问 B+ 树中数据的一种遍历机制。

它不会每访问一个元素都重新从根结点开始查找，而是定位到某个叶子结点后，沿着叶子结点之间的链表继续向后遍历。

### 4.2 作用

迭代器主要用于实现 B+ 树的顺序扫描和范围查询。

例如从某个 key 开始遍历后，可以依次访问后续所有有效的 Key-RID 数据，因此非常适合数据库中的范围查询、索引扫描等操作。

由于叶子结点本身已经按照 key 有序排列，并且与前后叶子结点相互连接，所以 Iterator 可以高效地连续访问数据，而不需要反复从 Root 进行搜索。

### 4.3 实现方式

Iterator 内部主要保存当前叶子页、当前元素下标以及 Buffer Pool Manager。

`Begin()` 从最左侧叶子结点开始，找到第一个有效元素；`Begin(key)` 先找到 key 所属的叶子页，再定位到第一个大于等于该 key 的有效元素；`operator++` 负责向后移动，当当前叶子页遍历结束时，通过 `next_page_id_` 进入下一个叶子页。

遍历过程中需要跳过已经被 Tombstone 标记的数据。当不存在下一个有效元素时，Iterator 进入 `End()` 状态。

## 5. B+树的并发控制

### 5.1 两类并发问题

| 问题                           | 说明                                                                                                      | 失去保护后的后果                                               |
| ------------------------------ | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **并发修改同一结点**     | 多个线程同时读写同一结点中的键数组、指针以及 size 等元数据                                                | 可能导致键值错乱、指针错误，以及 size 与实际不一致             |
| **遍历过程中的结构变化** | 一个线程正在沿 B+ 树向下遍历时，另一个线程可能同时执行结点的 Split、Merge，并修改父结点中的分隔键和子指针 | 当前线程可能读取到中间状态，走错子树，甚至读不到本应存在的 Key |

因此，B+ 树的并发控制不仅要保护单个 Page 内部的数据修改，还需要保证在 Split、Merge 等结构调整期间，其他线程不会观察到不一致的树结构。

### 5.2 解决方案

让多线程安全并发读改 B+Tree 的协议，要诀是「先拿子、再放父」，沿树逐层横移如螃蟹：

- **规则**：先取父节点闩锁，再取子节点闩锁；若子节点安全，即可释放父节点闩锁并继续下探；否则保留祖先锁。
- **安全**：该节点不会因本次操作分裂/合并——插入时「未满」，删除时「超过半满」。
- **查找**：全程只用读锁，持子锁即可放父锁，读读兼容，并发度最高。
- **插入/删除**：进子节点即取写锁；子节点安全 ⇒ 它不会改动父节点 ⇒ 可释放全部祖先锁；若一路都不安全（分裂/合并可能逐层上推），祖先锁须保留到改完。

### 5.3 提升性能

- **动机**：悲观路径做插入/删除时第一步就给根加写锁，高并发下根成瓶颈；而绝大多数修改并不触发分裂/合并，只改叶子。
- **做法（快路径）**：像查找一样全程读锁降到叶子，只在叶子加写锁；叶子安全就直接改完释放。
- **回退（慢路径）**：叶子不安全时释放全部锁，退回悲观写锁蟹行重跑一遍。
- **权衡**：常规情况根只被读锁「路过」，不阻塞他人；代价是失败时多走一遍遍历，但失败属少数，整体更快。

## 6. B+树与其他索引的对比

### 6.1 B树

B 树是一种多路平衡搜索树。一个结点中可以存放多个 key，并拥有多个子结点。

它和 B+ 树最大的结构区别在于：

> B 树的内部结点和叶子结点都可以保存实际数据。

结构可以简单理解为：

```text
        [20, 40]
       /    |    \
  [5,10]  [30]  [50,60]
```

其中内部结点中的 20、40 不仅用于导航，也可以对应真实数据。

B 树同样保持所有叶子位于相同高度，因此查询、插入和删除都能保持较稳定的复杂度。

### 6.2 LSM Tree

LSM Tree（Log-Structured Merge Tree，日志结构合并树）是一种面向高写入吞吐设计的存储结构。

它并不是像 B+ 树那样直接在磁盘 Page 上原地修改，而是：

> 先把写入放到内存中的有序结构，再批量写入磁盘，最后通过 Compaction 合并多个有序文件。

结构可以简单理解为：

```text
写入
 ↓
MemTable（内存）
 ↓
SSTable Level 0
 ↓
SSTable Level 1
 ↓
SSTable Level 2
 ↓
 ...
```

其中：

- **MemTable**：内存中的有序数据结构。
- **SSTable**：磁盘上的有序不可变文件。
- **Compaction**：将不同 SSTable 合并、去重和整理。

因此 LSM Tree 的核心思想是：

> 把随机写转换成顺序写，提高写入性能。

### 6.3 三者区别

| 对比项                 | B树                          | B+树                       | LSM Tree                     |
| ---------------------- | ---------------------------- | -------------------------- | ---------------------------- |
| **基本结构**     | 多路平衡搜索树               | 多路平衡搜索树             | MemTable + 多层 SSTable      |
| **数据存放位置** | 内部结点和叶子结点都可存数据 | 实际数据主要存放在叶子结点 | 分布在内存和多个 SSTable 中  |
| **内部结点作用** | 导航 + 数据存储              | 主要负责导航               | 没有传统的树形内部结点       |
| **叶子结点连接** | 通常没有专门链表             | 通常通过链表连接           | 不依赖叶子链表               |
| **范围查询**     | 支持，但不如 B+ 树方便       | 很适合                     | 支持，但可能需要合并多个层级 |
| **单点查询**     | 较高效                       | 较高效                     | 可能需要检查多个层级         |
| **写入方式**     | 原地修改结点                 | 原地修改 Page              | 先内存写入，再顺序刷盘       |
| **结构维护**     | Split / Merge                | Split / Borrow / Merge     | Flush / Compaction           |
| **写入吞吐**     | 中等                         | 中等                       | 通常较高                     |
| **适合场景**     | 一般多路索引结构             | 数据库索引、范围查询       | 写密集型 KV 存储             |

### 6.4 核心区别

**B树与B+树：**

最主要的区别是数据存放位置。

B 树的内部结点也可以存放实际数据，而 B+ 树的实际数据集中在叶子结点。这样 B+ 树的内部结点可以容纳更多分隔键和子指针，使树的分支更多、树高更低。

同时 B+ 树的叶子结点通过链表连接，因此更适合范围查询和顺序扫描。

**B+树与LSM Tree：**

两者最大的区别是写入方式。

B+ 树采用原地更新，直接修改目标 Page，并通过 Split、Merge 等操作维持树结构。

LSM Tree 采用追加写和批量合并，先把数据写入内存，再生成 SSTable，最后通过 Compaction 整理。

### 6.5 为什么数据库索引通常使用 B+ 树

数据库索引经常采用 B+ 树，主要是因为它非常适合磁盘和页式存储场景。

首先，B+ 树的分支数很大，树高很低。内部结点只保存分隔键和子页指针，因此一个 Page 中可以容纳大量 key。即使数据量很大，通常也只需要访问少量页面就能定位到目标记录，从而减少磁盘 I/O。

其次，B+ 树非常适合范围查询。所有实际数据都存放在叶子结点中，并且叶子结点之间按 key 顺序连接，因此找到范围起点后，可以直接沿叶子链表向后扫描。

另外，查询性能比较稳定。所有叶子结点位于同一层，B+ 树始终保持平衡，因此点查询、插入和删除通常都能保持在 O(log N) 级别。
