## 二、项目概述

Project 3 主要补全 BusTub 从查询计划到结果输出的执行链路。BusTub 的 SQL 处理流程如下：

Parser（解析）→ Binder（绑定）→ Planner（生成计划）→ Optimizer（优化计划）→ Executors（执行计划）

3. **Task 3**：实现哈希连接，并将满足条件的嵌套循环连接优化为哈希连接；

## 三、基础知识

### （一）查询执行模型

BusTub 的执行器以火山模型（Iterator Model）为基础。每个算子都实现 `Next()`，由父算子不断调用子算子并向上获取结果。这种模型结构清晰，算子之间也容易组合，但逐行执行会产生较多函数调用；Join、Order By 等算子还需要等待子算子完成后才能继续处理。

数据库中常见的执行模型还有物化模型和向量化模型：

- **火山模型**：每次返回一条记录，实现简单、组合灵活，但函数调用次数较多；
- **物化模型**：一次处理并输出全部结果，适合数据量较小的查询，但中间结果会占用较多内存；
- **向量化模型**：每次处理一批记录，可减少函数调用，并结合列式存储和 SIMD 提高分析型查询的效率。

BusTub 当前的实现更接近"行式批处理"：`Next(tuple_batch, rid_batch, batch_size)` 每次返回一批 Tuple，但批次内部仍采用行式数据，并不具备典型列式向量化执行的全部特征。

| 模型                         | 特点                                                                                                                                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **火山模型**           | 每次 `Next()` 返回一条记录；接口简单、算子容易组合；但函数调用频繁，逐行处理开销较大                                                                                                                           |
| **物化模型**           | 算子处理完全部输入后一次性输出结果；调用次数少，适合结果较小的查询；但中间结果占用内存，上层提前结束时容易浪费计算                                                                                               |
| **向量化模型**         | 每次 `Next()` 返回一批记录；减少函数调用，并可结合列式布局与 SIMD，更适合 OLAP 等吞吐型负载；但实现复杂，小数据集上的优势不明显                                                                                |
| **BusTub：行式批处理** | 调用形式为 `Next(tuple_batch, rid_batch, batch_size)`；保留火山模型，仍由父算子逐层拉取结果；引入批处理，一次最多返回 `batch_size` 条记录；与典型向量化的区别在于批次内部仍是行式 Tuple，没有列式布局与 SIMD |

### （二）执行器的基本约定

执行器需要遵守以下三个约定：

1. `Init()` 用于初始化运行状态，并且可能被重复调用，因此要重置迭代器、游标和执行标记；
2. Tuple 保存记录内容，RID 表示记录在表中的物理位置，两者必须按下标一一对应；
3. 聚合、连接等计算类算子产生的结果没有真实 RID，需要使用空的 `RID{}` 占位。

即执行器契约：`Init()` 可重复调用，必须重置迭代器、游标和完成标记；Tuple 与 RID 一一对应；计算结果没有真实 RID 时使用 `RID{}` 占位。

## 四、项目实现

### （一）执行器与存储层的衔接

以顺序扫描为例，`SeqScanExecutor` 先通过 `ExecutorContext` 获取 Catalog，再根据表名找到 `TableInfo`，从中取得 `TableHeap` 和 `Schema`，最后使用 `TableIterator` 遍历数据。

执行器并不直接管理数据页。页面读取、写入和淘汰仍由缓冲池负责，因此 Project 2 实现的 B+ 树索引可以直接作为 Project 3 的访问路径。

| 组件                        | 职责                                                                                                                                                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ExecutorContext**   | `GetCatalog()` 是执行器访问元数据的入口                                                                                                                |
| **Catalog**           | `table_names_`：表名 → 表 OID；`tables_`：表 OID → TableInfo；`index_names_`：表名 → 索引名 → 索引 OID；`indexes_`：索引 OID → IndexInfo    |
| **TableInfo**         | `schema_` 描述列名、类型和顺序；`table_` 指向 TableHeap                                                                                              |
| **TableHeap**         | 页面链表，由 `first_page_id_` 和 `last_page_id_` 维护；TableIterator 顺序遍历记录并返回 Tuple 与 RID；记录操作包括插入元组、读取元组、更新 TupleMeta |
| **TablePage**         | TupleMeta 保存时间戳和 `is_deleted_` 删除标记；Tuple 数据按照 Schema 序列化存储                                                                        |
| **Tuple 与 RID**      | Tuple 是记录的实际内容；RID = page_id + slot_num，定位记录的物理位置；扫描输出中 `Tuple[i]` 必须对应 `RID[i]`                                        |
| **IndexInfo**         | B+ 树索引，索引键 → RID；IndexScan 先查索引得到 RID，再回 TableHeap 读取 Tuple                                                                          |
| **BufferPoolManager** | 负责页面读取、写入、固定与淘汰；执行器不直接管理页面                                                                                                     |

### （二）扫描类执行器

`SeqScanExecutor` 按照表中的物理顺序遍历记录，跳过已删除元组，并使用 `filter_predicate_` 判断记录是否满足查询条件。

`IndexScanExecutor` 包含两种扫描方式：

- **点查询**：根据 `pred_keys_` 调用 `ScanKey` 获取候选 RID；
- **范围扫描**：通过 `GetBeginIterator()` 和 `GetEndIterator()` 遍历索引。

索引中保存的是键和 RID，因此两种方式都需要回表读取完整元组，并再次检查删除标记和过滤条件。

### （三）修改类执行器

`InsertExecutor` 在插入表记录后，还需要为该表上的所有索引添加"键 → RID"映射。

`DeleteExecutor` 使用逻辑删除，只修改 TupleMeta 中的 `is_deleted_` 标记，不直接回收页面空间。这样可以避免页内数据移动，也方便后续进行事务回滚。

`UpdateExecutor` 的处理过程更复杂：先根据旧记录计算新记录，再删除旧索引项并将旧记录标记为已删除，最后插入新记录并建立新索引项。即使索引列的值没有变化，也必须重新建立索引项，因为新记录对应的是新的 RID。

### （四）聚合与连接执行器

![图 4 BusTub 执行器的父子调用关系](/posts/week6-QueryExecution/image-002.png)

`AggregationExecutor` 是流水线中断器。它会在 `Init()` 中读完子执行器的结果，并按照分组键建立聚合哈希表；`Next()` 只负责输出已经计算好的聚合结果。

聚合结果的 Schema 由 Group By 列和聚合列组成。需要特别注意：当输入为空且没有 GROUP BY 时，仍然要输出一行结果，其中 `COUNT(*)` 为 0，其他聚合值为 NULL。

| 环节                          | 说明                                                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **输入记录**            | 计算分组键：由 Group By 表达式生成 AggregateKey；计算聚合输入：由聚合表达式生成 AggregateValue                                           |
| **AggregateKey**        | GroupByKeys：每个分组表达式对应一个 Value；NULL 比较时两侧都是 NULL 应视为同一个分组，普通比较返回 CmpNull，若不单独处理会把同组错误拆开 |
| **AggregateValue**      | `vector<Value>`，每个聚合表达式对应一个槽位；初始值 `COUNT(*)` 为 0，其他聚合值为 NULL                                               |
| **InsertCombine**       | 新分组：先生成初始值，再合并当前记录；已有分组：更新 COUNT、SUM、MIN 或 MAX                                                              |
| **AggregationExecutor** | `Init()`：Build 阶段读完孩子，将所有记录写入聚合哈希表；`Next()`：Output 阶段遍历哈希表，拼接分组列和聚合列                          |
| **输出 Schema**         | Group By 列 + 聚合列                                                                                                                     |
| **空输入语义**          | 有 GROUP BY：没有任何分组，因此输出 0 行；无 GROUP BY：仍输出 1 行，`COUNT(*) = 0`，其他聚合值为 NULL                                  |

图 5 AggregationExecutor 的哈希聚合流程与空输入语义

`NestedLoopJoinExecutor` 会为每条左表记录扫描右表，因此需要在多次 `Next()` 调用之间保存当前批次、游标和匹配状态。

`NestedIndexJoinExecutor` 只有一个外表子执行器。它根据外表元组计算连接键，再通过内表的 B+ 树索引获取 RID 并回表。对于左外连接，如果没有匹配记录，需要按照右表 Schema 构造一组对应类型的 NULL。

## 五、遇到的问题

### （一）索引迭代器导致同线程自死锁

`IndexScanExecutor` 的索引迭代器会持有叶子页的读锁。如果 Update 的子节点是 IndexScan，Update 随后删除同一索引项时又会申请该页的写锁。由于读锁尚未释放，同一线程会一直等待自己持有的锁，从而发生自死锁。

**问题过程**（成员迭代器让读锁存活过久）：

1. UpdateExecutor（同一线程）通过 IndexScanExecutor 的成员迭代器获取待更新的元组；
2. 使用成员迭代器扫描索引，读取叶子页并持有读锁；
3. 返回元组与 RID；
4. `DeleteEntry()` 请求同一叶子页的写锁；
5. 等待读锁释放——扫描返回后成员迭代器仍然存活，读锁未释放；
6. 读锁和写锁属于同一执行线程，形成自死锁。

**修复方法**（先扫描并收集 RID，再执行修改）：

1. UpdateExecutor 创建局部迭代器；
2. 持有读锁并完成扫描，收集全部目标 RID；
3. 离开作用域，局部迭代器析构，释放读锁；
4. 返回已缓存的 RID；
5. `DeleteEntry()` 请求写锁，写锁获取成功，完成修改。

重新初始化索引扫描时，也要先释放旧迭代器占用的页面资源。

### （二）Update 再次扫描到新插入的记录

Update 会在表尾插入新记录。如果扫描范围随着表尾继续增长，新记录可能再次满足更新条件，导致重复更新，严重时甚至出现死循环。

顺序扫描可以通过固定本次扫描的结束位置解决；索引扫描则应先收集所有待更新 RID，再执行修改，避免一边扫描一边更新索引。

### （三）修改类执行器被重复执行

Insert、Delete 和 Update 在一次查询中只能生效一次，但上层可能多次调用它们的 `Next()`。因此需要增加 `is_executed_` 标记：在 `Init()` 中设为 false，第一次执行完成后设为 true，之后直接返回 false。

SeqScan 和 Values 属于叶子算子，可以通过迭代器或计数器自然结束，不需要这一标记。

### （四）空表聚合没有输出结果

原实现只有在读到输入记录后才建立分组，导致空表聚合直接返回零行。正确做法是在没有 Group By 且聚合哈希表为空时，主动加入一条初始聚合结果。

### （五）NULL 分组键无法合并

两个 NULL 使用普通比较会得到 CmpNull，而不是 CmpTrue。如果直接按比较结果判断，相同的 NULL 分组键会被错误地分到不同组中。

因此，比较分组键时要单独处理：如果对应位置都为 NULL，就视为相等并继续比较下一列。

### （六）OR 条件产生重复结果

例如：

```sql
SELECT * FROM t WHERE v1 = 1 OR v1 = 1;
```

两个分支会通过索引找到同一个 RID。如果直接合并结果，同一行会被输出两次。解决方法是使用集合对 RID 去重，只保留第一次出现的记录。

### （七）执行状态没有跨批次保存

一次 `Next()` 不一定能处理全部输入。如果把迭代器、批次位置和匹配状态定义为局部变量，下次调用时就会丢失执行进度，造成重复输出或漏行。

这些状态应保存为成员变量，并在每次 `Init()` 时统一重置。

## 六、本周总结

本周完成了 Task 1 的主要执行器和 SeqScan → IndexScan 优化规则，并通过了本地与线上测试。通过本阶段的实现，进一步理解了查询计划如何驱动执行器，以及执行层如何调用表和索引完成数据访问。

本周最主要的收获有三点：

1. 批处理执行器必须在多次 `Next()` 之间正确保存运行状态；
2. Insert、Delete 和 Update 不仅要修改表数据，还要同步维护所有相关索引；
3. 索引迭代器持有的页面读锁可能与后续写操作冲突，修改数据前必须及时释放相关资源。
